# 行程方案规则（流程二的出行安排）

> 本文件由 `SKILL.md` 指向。**进入流程二步骤 10（生成旅游出行方案）时读**——**只有客户在步骤 8 选了「是」才会走到这里**。

### 行程方案规则（流程二的出行安排）

景区间移动类别由第一阶段决定：**自驾**（含"已在目的地·自驾"）或**公共交通**（含"已在目的地·非自驾"与城际公共交通已选方案者）。两类各自给出不同方案，见下。任何方案都要标注：路线顺序、每段交通方式与距离/时长、总时长、估价依据。

**通用要求（两类都遵守）**：
- **省步数四条（第二轮 A/B 实测踩出来的）**：
1. **先产骨架，再补文字**：`node scripts/itinerary.js emit <plan.json> --out data.json` 直接把行程页 data.json 的骨架生成好（封面卡 / 总览表 / legs 距离都算完，只留「方式 / 耗时」待填）——你只补这两列与每段的 bus / taxi 文案，**不要从空 JSON 手写**。
2. **两两距离一次算完**：`itinerary.js dist anchors.json --out dist.json` 只产出**矩阵对象**（键＝起点/景点，值＝两两 km）；串线要把这个矩阵**嵌进 `plan.json` 的 `dist` 字段**再跑 `node scripts/itinerary.js <plan.json>`（**默认模式就是串线，没有 `chain` 子命令**；起点用 `--start <名称>` 覆盖）。**不要**"先跑一次 `dist`、再手写一遍距离字典、再跑一次串线"（实测重复了一遍）。
3. **要查的只有"每个景点距锚点（到达站/市中心）的里程与方位 `dir`"**——这一项**每个景点最多查 2 次**；查不到就交给 `dist` 推算并注明"参考约数"。**不要为凑精确值反复搜索**。**取数时机**：客户在步骤 8 选了「是」、并在步骤 9 定下起始点之后才取——**不在选景点之前预先收集**（路线规划有变数，提前收必浪费）。
4. **换乘走法（哪条地铁线、几站、多少分钟）**：同一条线路**最多查 2 次**；查得到就写站点级，查不到就写"按地图软件推荐，以现场为准"——**不要为每一段都单独检索**。
- **客户自行补充的景点一并纳入（硬性）**：客户在「是否需要景点路线规划」框的输入框里补充的景点，与本行程**一并串联**（**不回退、不重新生成景点推荐页**）；它们的**两两距离与接驳照同一口径取**，**开放时间与闭馆日也要查**（查不到写"以景区公示为准"），并在**行程页与聊天回复里标明是客户自行补充的**。
- **不按游玩天数拆分**：整条串线从起点一站站排下去即可，不写"D1/D2/住宿/建议天数"；用户在意天数时再另说。**行程时间由用户自行安排**——本 skill 只给路程规划（顺序、路段、方式、耗时、费用），不排具体时刻表（几点到几点玩）。
- **站点级详细（关键）**：每段都要写清「**从哪个站上车 → 坐哪路/哪个班次 → 到哪个站 → 如何换乘/步行 → 到景区**」与费用、耗时。参考**高德地图的路线**或**公路客票班次**，不要只写"打车 X km"这种粗略表述；打车/包车作为省时备选另列。
- **首段的出发地按「出发点选择框」的结果定**（两种情形）：
  1. 用户选**「从到达地出发，选最近的景点作为起始点」** → 起点 = 距参照物**最近**的那个景点。**参照物**：城际到达→**到达站/机场**、已在目的地→**市中心**、自驾→**靠近目的地的高速路口**；
  2. 用户选**「我来自己决定第一个景点（下方输入）」** → 起点 = 用户在下方输入的**那个景点**。
  之后**一律按最近邻一路串联**——**这一步交给 `scripts/itinerary.js` 算，不要在文字里排**（给定两两距离，顺序唯一；模型手排既贵又可能每次排出不同结果）。脚本同时给出每段里程、总里程，并给出每段里程与总里程。**两两距离怎么来**：优先按「站点级详细」查地图路线；**查不到就交给 `itinerary.js dist` 推算**——你只查每个景点「距市中心 / 距到达站」的里程，**并尽量带上方位 `dir`**（N/NE/E/SE/S/SW/W/NW 或角度），写成 `{ "start": "锚点名", "spots": [{"name":"X","km":25,"dir":"SE"}, …] }`，跑 `node scripts/itinerary.js dist <anchors.json> --out dist.json`（**默认就是 1.15**（留 15% 余量）；要精确不留余量显式写 **`--margin 1`**）：**给了方位它用余弦定理算，没给才退回"里程差值"并会告警**（差值假定两点同向，不同向会严重低估，实测差过 7 倍）。**不要自己算 N²/2 对减法。**单位 km、只需给单向值**（脚本按对称处理）。它产出的 `dist` 直接当 `dist` 字段用，**但属参考约数**，页面与聊天里必须注明"里程为参考约数"；**不要为凑精确值反复搜索**（贵且无收益）。完整用法跑 `node scripts/itinerary.js --help`。
- **两套方案：A 最快（里程最少） / B 避峰（错开人流高峰）**（口径 2026-10-18 定）：
  - **A（最快）**：交给 `node scripts/itinerary.js <plan.json>`（最近邻，顺序唯一，只在里程上最优）。
  - **B（避峰）**：交给 `node scripts/spots_peak.js <spots-peak.json> --arrive HH:MM [--holiday] [--max-detour 20]`。它只用**数据里的事实**判断：低峰窗＝「开园后 120 分钟」与「闭园前 150 分钟」两个窗口；代价＝里程 + 0.15×热门景点错过低峰窗的分钟数 + 3×热门落入中段（`--holiday` 时权重翻倍为 6）；用**多起点贪心**选全局代价最小顺序（局部贪心会漏掉"先跑远的热门"）。
  - 输入 `spots-peak.json`＝`{start, arrive, dist, spots:[{name, hot, open, close, dwellH}]}`；`dist` 可直接用 `itinerary.js dist` 产出的矩阵；`hot` 看景点是不是热门、`dwellH` 用 meta 里的建议游览时长。
  - **两套都交付（有条件）**：`spots_peak.js … --emit-plan <itin-data.json> --out <data.json>` 会把 `plans[]` 和 `overview.footnotes` 写进行程页 data.json；卡片里写清总里程与"比最快多 X km / Y 分钟"，**由客户选**。⚠ 只有 `fallback=no`（避峰成立且里程增幅 ≤ `--max-detour`）才是两张卡；`fallback=yes` 只写最快一张，并在页面写清"本线路避峰不成立 / 超里程上限"的原因。
  - **退让（硬性）**：避峰里程增幅 > `--max-detour`（默认 20%）或有时段塞不进 → `fallback=yes`，**默认只交付最快方案**并在页面写原因；只有客户**明说"愿意多跑路换人少"**时才给备选，并写清多跑多少。
  - **不许说"已避开人流 / 保证不排队"**：本技能没有客流数据，只能写"排在开园后低峰窗（例：开园 08:30 → 08:30–10:30，按实际开园 +120 分钟算）"这种**可核对的时段结论**，并注明"按开闭园时间推断"。
- **开放时间提示（必做）**：行程方案中，每个景点标注**开放参考时间/闭馆日**，并给出提示——① 对该景点的**闭馆日**给**星期级提示**（如"该馆周一闭馆，请避开周一"）——**本技能不规划游玩天数、也不知道客户哪天去哪个景点**，所以**一律按查到的闭馆日说、不要默认周一**，**不要把闭馆日套到某个具体日期上**；② 若**到达时刻较晚**（如傍晚到站），提醒"首站景点届时可能已闭园，建议次日或调整首站"。只给提示，不替用户排时刻表。**闭馆日与开放时间一律以最近公告为准**；查不到就写"以景区公示为准"。
  - **通用口径（所有分支）**：本技能**只收集出发日期、不收集停留天数**，也**不按天排行程**——所以闭馆日提示一律是**星期级**的（"该馆周一闭馆，请避开周一"），**不得假定用户的出行日就是周一**，也不要把闭馆日绑到某个具体日期上。**只有客户自己主动说出停留日子时**，才按那几天精确提示。

#### 一、自驾（自己开车玩景区）——只给自驾方案（行车路线）+ 依据

- **只给自驾路线，不查也不写公共交通**；目标是**行驶路程最短**（不是时间估算）。
- **起点**按「出发点选择框」定（自驾以**靠近目的地的高速路口**为参照）；**接续按最近邻串联**，自驾取**行驶距离**最近者。
- **完整口径**（逐段标注要求）见 **`references/driving-itinerary.md`**（**客户选自驾时才读**）。

#### 二、公共交通（不自己开车玩景区）——给多种交通方式方案 + 估价

参考地图软件的方案组合（每类给 1 个代表方案，并估算费用与耗时）。每段移动方式标注清楚；以下**三套方案（全文统一称「公共交通三方案」= 全程打车 / 公交+打车 / 公交+步行）都要给出估价**（金额按当地计价估算，注明"估算"）：

1. **全程打车方案**（最省心）：从起始点（到达站/机场或市中心）到每个景点全程打车/网约车。估价 = 起步价 + 每公里单价 × 总里程估算。
2. **公共交通 + 打车组合**（按地图软件推荐给出两个变体）：
   - **省钱方案**：能坐公交/地铁的段坐公共交通，接驳不便段打车，费用最低；
   - **最快方案**：以到达时间为准选最快走法，但**不能全程打车**——至少有一段用公共交通/步行（体现"省时间但兼顾性价比"）。
3. **公共交通 + 步行方案**（最省钱，体力换钱）：优先公交 + 步行可到达的串联，打车仅作兜底或不用。

- 估价口径：公交按单程票价；打车按公里计价（注明所在城市计价规则差异、是否含等候/高峰溢价）；总估价给出区间，标注"实际以计价为准"。
- 起点与接续：按「通用要求」的参照口径与最近邻串联。
