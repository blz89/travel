# 自驾 · 路线规划口径（城际高速避堵 ＋ 电车充电点）

> 本文件是 `travel` 技能的**参考资料**，由 `SKILL.md`「自驾路线规划规则」指向。
> **只在「出行方式 = 自驾」且客户在「是否需要进行自驾路线规划」框选了「是」时才读它。**
> **范围 = 出发地 → 目的地 这段城际自驾**；**景点之间的路线**另按 `references/driving-itinerary.md`（由流程二步骤 8 那个框决定）。
> **仅适用于中国大陆（内地）**。
> **输出形态已定（2026-10-07）＝「地图 App 渲染截图（图）＋ 单文件讲解页（文）」**：把**起终点（必要时 +1 个走廊 `vias`）**交给**地图厂商的网页版**，让**它**把路线画出来、截图；再把截图**内嵌进一份零外链讲解页**，逐项讲清这条线为什么这么走。细则见 §8。

## 1. 先收齐三项输入（顺序固定；**每个弹框只问一件事**）

| # | 弹框 | 说明 |
|---|---|---|
| 1 | **计划出发日期 + 时间** | **问题文本必须强调"请填日期"**；框内要写清「**哪一天 + 几点**」（例：`10 月 1 日 早上 7 点`）——带日期 → 按该日期判节假日（见 §2）；**只填了时刻 → 紧接着补问一句「具体是哪一天？」**，**拿到日期才继续** |
| 2 | **车辆类型** | 选项只有 **电车 / 油车** |
| 3 | **希望行驶多少公里后充电** | **只有电车才问**；**可填「否」→ 默认 200 公里**；客户给了数字就用客户的，**不要替他改** |

- **油车不问第 3 项**，也不做任何充电规划。
- 三项收齐即可**后台发起**拥堵研究（**可与景点预研并行**，不阻塞提问与已就绪的交付）。
- 本框只属于**出行方式 = 自驾**；**「已在目的地·自驾到达」没有城际驾驶段，不做本框、不做本节规划**。

## 2. 判「出行日类型」，过闸门（一次判断，最多查 2 次）

- **节假日 / 免费通行期**：法定节假日及**前后各 1 天**；**春节 / 清明 / 劳动节 / 国庆节**这 4 个假期**高速免费**（7 座及以下小客车；**假期首日 00:00 → 末日 24:00，按出收费站时间算**）。依据 = 国务院办公厅当年节假日安排通知 + 交通运输部「重大节假日免收小型客车通行费」公告。
- **周末 / 工作日**：**按非节假日处理**（见闸门）。

### 闸门（硬性）：**只有节假日才做拥堵分析**

| 出行日 | 做什么 | 不做什么 |
|---|---|---|
| **节假日**（法定节假日及**前后各 1 天**，含 4 个免费通行假期） | 走 **§4 五步流程**（先查缓存 → 收集 → 分析 → 结论 → 输出 → 保存）＋ §5 节点排名 ＋ §6 绕行设计 | — |
| **非节假日**（工作日、**普通周末**、调休后的平日） | **直接给「正常最短路径」（同一旧名，实义＝地图默认推荐线：全程高速、耗时最短）**：§3 取最快线 → §7（**只有电车**做充电点）→ §8（截图 ＋ 讲解页；网页版链接上的 `policy` 参数实测无效，默认就是最快线） | **不做拥堵分析**：不查缓存、不收集、不统计、**也不设计下道绕行** |
| **日期还没问清**（客户只给了时刻） | **先补问一句「具体是哪一天？」**（同一件事的追问，不算新增问题）；**拿到日期后**再按上面两行判定 | **不许靠猜**，也不做拥堵分析 |

- **例外**：客户在**非节假日明确要求避堵**（"那天说会堵""想绕开堵点"）→ 才按 §4 处理，并在回复里注明"**这是按你的要求额外做的**"。
- 判定依据仍是国务院办公厅**当年**节假日安排通知 + 交通运输部免费通行公告；**查不到就按"不确定"处理**（保守但不浪费）。

## 3. 主线：地图的「最快路线」（**不重塑走廊**）

- **取法**：让地图按「起终点」算**最快路线**（网页版直接就用默认最快线；要脚本/批量算用接口 `strategy=32`——URL 上的 `policy` 网页版实测无效）；网页版面板同时给多条备选时，**取耗时最短的那些**（可为 1 条或并列的全部）。记下**里程 / 耗时 / 途经高速编号集合**（＝后面的「路线指纹」）。
- **地图只当「算路器」与「出图器」**：**"这条路是推荐线"不构成任何避堵结论**，但也**不是"离经叛道"的理由**——**改线必须由证据驱动**（§5 的压线段落），并且**算清代价**。
- **实测反例（癸市→子县 · 10 月 1 日，务必记住）**：自钉 8 个途经点去"重塑走廊" = **1755.8 km / 20.70 h**；而地图最快线 = **1623.9 km / 16.24 h** —— **白多约 130 km、约 4 小时**。**"我们自己绕得更聪明"是错觉。**
- **「太绕」判据（硬性）**：与最快线**同起终点**比较，**里程增幅 ≤ 20%** 或 **耗时增幅 ≤ 30 分钟**——**满足其一即算候选**；**两个都超**才算**太绕**，不纳入分析、也不用于规划（顶多一句话说明它存在）。

## 4. 沿主线取证：**收集 → 分析 → 结论 → 输出 → 保存**（**先查缓存：命中就不收集**）

**路线指纹** = **起终点 + 途经高速编号集合**（如 `壬市→子县 | G9101/G9102/G9103/S9104/G9105`）。先用指纹查一次结论库：

```bash
node scripts/traffic-history.js data/high-congestion/segments.json --match "G9101,G9102,G9103,S9104,G9105" --corridor --top 20
```

- 输出首行就是**缓存判定**：**HIT**（覆盖 **≥3 个年份** 且 **最新年份 ≥ 今年-1**）→ **直接复用库里的结论、跳过收集**（回复里注明"数据年份 + 来源数"）；**MISS** → 走下面 ①→②→③→④→⑤，**且必须在 ⑤ 保存后再输出**。
- **同一条走廊第二次规划就直接命中缓存**，不再重复检索（这是本节的省时主路径）。

**① 收集（只在 MISS 时做）**

- **来源**：交通运输部 / 省交通运输厅 / 公安交管 / 高速集团 的**节假日出行提示与运行通报**、权威媒体点名；**逐年**检索（窗口 = **近五年**）。**每个路段最多查 2 次**。
- **预算（硬上限）**：整条走廊 **`web_search` ≤ 12 次 + `web_fetch` ≤ 6 次**；**拿到 ≥3 个年份的记录即收敛**，不追求凑满 5 年。
- **每条记录必须带**：**年份 / 节假日 / 省 / 高速编号+名称 / 路段原文（照抄，不归并） / 类型（预测·实测） / 发布单位 / 来源URL / 发布时间**。
- **查不到就写「未获取」（即"无公开数据"）**，不许编造路段名、桩号、单位、链接。落到 `data/high-congestion/segments.json` 的 `records[]`：**增量追加，不要重写整库**。

**② 分析**（地名归并 + **按「年·节假日」计次**）

```bash
node scripts/traffic-history.js data/high-congestion/segments.json --corridor --top 20
node scripts/traffic-history.js --check data/high-congestion/segments.json    # 提交前必须 PASS
```

- **命中单位 = 年 + 节假日**（同一年国庆与春节算**两次**）；**同地异写法自动归并**（输出里有"别名数"）；**实测 > 预测**，排序时实测优先。

**③ 结论**：得到「走廊高频地点组 Top N」，每项含 `命中次数 / 命中明细（年·节假日）/ 覆盖年份 / 实测次数 / 来源数`。**必须写明两条口径**：① 这是"**被官方反复点名**"的频率，**不是逐段实测概率**；② 粒度不统一（有的到枢纽/桩号，有的只到"XX段"）。

**④ 输出**：见 **§8**。**⑤ 保存**：新增记录写回 `records[]`，跑一次 `--check` 确认 PASS。

- **只存我们的统计结论与来源引用**；**厂商接口返回的原始路况/几何数据一律不落盘**（红线：**地图 API 的原始响应不得落盘**）。库随年份**滚动更新**。

> **实时核对（本节，出发日 24 h 内 / 当天必做）**：用 `v3/direction/driving?extensions=all` 的 `tmcs` 看**此刻**哪段缓行/拥堵 → 触发**下道绕行 / 错峰**（口径见 §6）；需要按区域看时用 `v3/traffic/status/circle`。**实时数据只在内存里用、不进库、不落盘**。

### 能力边界（实测 2026-10-09，必须照实写进页面）

| 能力 | 实测结果 | 对我们的约束 |
|---|---|---|
| **未来出行 / 节假日预测接口** | **无权限**（`/v3/etd/driving` → `10002 SERVICE_NOT_AVAILABLE`；`/v5/direction/etd/driving` → `10017`） | **未来某天"必堵"只能来自官方公告**；页面上**不许写"预测拥堵"** |

## 5. 节点：排名（**现阶段只排名、不打分**）

**入口**：`scripts/congestion-nodes.js <route.json> --date <出发日> --out nodes.json`（跑 `--help`）。

- **「压线」算法**：把点名路段**按地名定位**（POI / 地理编码取坐标），**算它离主线折线的最近距离，≤15 km 记为「压线」**（＝该节点在主线上，需要处理）。
- **自动防错（三条，缺一条排名就会失真）**：
  1. **省别校验**：记录的 `scope`（某省/某省/…）与定位结果的省份必须一致，否则丢弃；
  2. **路由核对（挡平行线）**：**锚点自带的道路名**（如「某县收费站（**G9106**戌高速出口）」）必须与记录的路名一致，否则判为**平行线**并剔除（实测剔掉 G9107 巳高速 @230 km、G9108 午高速 @951 km 两条假节点）；
  3. **地名三态验证**：`match` 采用 / `did-you-mean` 存疑（**不进排名**，写进"未获取"）/ `no-match` 丢弃。
- **排名依据（依次比较）**：**压线** → **命中次数（年 + 节假日计次）** → **最新命中年份** → **施工 / 隧道群 / 枢纽 / 省界** → **主线先后**。
- **评分制（数据齐了再启用）**：**历史拥堵次数 ≤5 分 ＋ 拥堵中位数时长 ≤5 分 ＋ 平均时长 ≤3 分 ＋ 最长时长 ≤2 分，>8 分 → 必须精细化**。**拿不到时长数据时只排名、不打分，不许编分数。**
- **卡点＝一个「点」**：**卡点坐标离主线 <1 km 才算压在我们行驶的线上**（实测：某枢纽 0.1 km＝在线上；某隧道 15.8 km＝在往壬市的另一条方向上，**不能当我们的卡点**）。
- **本库没有记录 ≠ 不堵**：没被点名只能写「**未发现被点名路段**」，**严禁写成"已避开拥堵"**。

## 6. 节点级绕行：**绕点不绕段**（先找走廊 → 再画线 → 算清代价）

**先比方案，再做预案**：主线定下来后，**只对排名靠前的节点**（默认 ≤3 个）动手；**没有证据就不要编绕行方案**。对每个要处理的卡点：

1. **上游下道口**：取**上游最近的收费站**（＝卡点之前最近的那个）下高速；**下游上道口**：取**卡点之后的下一个收费站**；**再上高速的节点可以提前或后退**，不限于紧邻收费站。
2. 走并行地面道路（国省道 / 县道）绕过卡点。
3. **下高速后必须同样分析地面路段是否拥堵（硬性，不得跳过）**——判据：是否穿过**城区 / 县城 / 集镇**、是否有**学校、集市、施工改扩建、热门景区出入口**、车道数是否骤减；给出该地面段的 **可行 / 需错峰 / 不可行** 结论。
4. **地面段也不可行时**，按优先级改用：① **换另一条高速** → ② **错峰**（前移 / 后移出发时间，**改的是时间，不是行程顺序**）→ ③ 维持原路线，但**标红写明「该段大概率拥堵，建议预留 X 小时缓冲」**。
5. **绕行必须算清代价并写出来**：多走的里程、多花的时间、过路费变化（下高速再上高速可能**分段计费**）；**绕行比堵着更亏时就不要绕**，改用错峰。
6. **落到逐段**：每段给「主路线（走高速）＋ 建议通过时段 ＋ 绕行触发条件（堵到什么程度改走地面、从哪个口下、从哪个口上）」；**若沿用现有行程页字段**，落点是 `legs[].bus` / `legs[].car` / `legs[].note`；**输出形态定稿前不要新造字段**。

### 6.1 绕行线的做法（分两步，全是实测踩出来的）

**第一步：先把「地面走廊」找出来（4 条）**

| # | 规则 | 为什么 / 实测 |
|---|---|---|
| A1 | **让地图用「不走高速」模式自己算走廊**（**网页版：点开页面里的「偏好」→ 选「不走高速」**，出图时用 `map-shot.js --pref 不走高速`；**URL 参数 `policy=3` 在网页版会被忽略，照样给高速——实测**）；**入口不通就换下一个出口再试** | 比手钉途经点可靠得多。实测：`某矿 → 寅镇`「不走高速」直接返回**未找到合适路线**（那一侧地面不通）；**换成下一个口 `某矿 → 卯镇` 就给出 52.2 km 纯地面线**（长兴路→富春路→**G9109**→卯镇互通，¥1，不折返）。**接口侧没有「不走高速」这个参数**：**v3 `strategy=1`（费用优先）才会绕开高速给出地面走廊**，v3 的 2 / 3 / 4 / 5 与 v5 的 3 / 10 / 32 / 33 **都跟默认同路**——实测 `午县收费站 → 未县西收费站`：默认 37.6 km／28 min／14 元（午县立交桥→锦绣大道→未县立交桥），`strategy=1` 给出 **40.3 km／48 min／3 元**（迎宾大道→固东线→固雄线，纯地面）；网页版点「偏好→不走高速」给出同一条 **40.3 km／48 min／¥3**（图上面板读数，与接口互证） |
| A2 | **按「整条线的总里程」比选，不是只看该段**；**入口越靠后不一定越好**；**比里程之前先验这条线真的没再回到原高速** | 实测（癸市→子县）：不绕 **1624.4 km**（仍穿堵段）；手钉的「绕寅镇」看着只多约 30 km，但**逐段指令显示它在 763 县道折返、最后仍回到 G9105 跑 23.7 km（假绕行，见 B4）**；真正可行的是「不走高速」自己算出来的 **某矿 → 卯镇 52.2 km 纯地面**（整条线代价更大，但确实不进 G9105）→ **绕行不是抄近路，是用里程换时间**，触发条件写清"堵段缓行 > 绕行代价" |
| A3 | **平行替代高速要先看「汇合点」在哪**：汇合点在堵段**上游端**＝绕不开 | 实测 S9110 某高速 在某矿互通附近就汇回 G9105（丑县服务区 → 寅镇 36.6 km 里最后 23.8 km 仍是 G9105） |
| A4 | **找不到可行地面线时，不许硬造绕行线** | 写「**不做地面绕行**」＋ **错峰** ＋ **就近服务区休整等待** ＋ **当天实时复核**，理由写进证据表；**图改成"卡点定位图"**——只画**拥堵段红线** ＋ 上下互通（标"不建议在此下道 / 上道"），**不画地面线** |

**第二步：再把线画对（7 条）**

| # | 规则 | 为什么 / 实测 |
|---|---|---|
| B1 | **途经点要"加密"：沿走廊每 10–20 km 钉一个**，按顺序排列，出 / 入各占一端 | 只给 1 个途经点，算路会**"到那个点再折回来"**——画出来就是来回 |
| B2 | **途经点取"压在国道路面上"的点**（`place/around` 搜**国道编号**如"324国道"，取**门址里写着自己**的点），**别钉村镇中心** | 村委会 / 镇政府本身偏在路边，会把线拽出**锯齿**（实测同一条线 50.9 km → 68.6 km）；按地名二次查询还会撞同名村（「安马村」被解析到 **30 km 外**） |

| B5 | **做"反向连通性"检查：A→B 与 B→A 里程差 3 倍以上 ⇒ 单向互通，该口不能用来上道** | 实测：寅镇收费站 → 邦驰驿站 13.1 km，反向 **49.8 km** ⇒ **寅镇互通进口侧不连通**；官方通告的分流方案在当前路网下**复现不出来**（当年可能靠临时匝道 / 现场组织） |
| B6 | **关键判断用两条独立途径互证**：网页版「**偏好→不走高速**」（`--pref 不走高速`）与接口 `strategy=1` 各算一次，**正向与反向各算一次** | 单途径容易把"有没有地面路"判反；实测两个途径对同一条走廊给出同一结论（某矿 → 卯镇 52.2 km 纯地面；午县 → 未县西同为 40.3 km／¥3；反向查询才暴露寅镇进口侧单向不通） |

## 7. 电车：沿途充电点规划（**只有电车做**）

- **车辆类型是油车 → 本节整节不做**（「如果不是电车可没有服务区推荐哦」）：**不规划充电点、不画蓝点、不推荐任何服务区**，讲解页**不设第②段充电清单**（该段整段省略、后面的段号顺延：① 总览图 → ② 拥堵解读表 → ③ 说明 → ④ 来源）。油车只做避堵路线；**别拿"服务区可以休息"当推荐理由**。
- 车辆类型是电车 → 按本节到 §7.1 执行。
- **间隔依据 = 客户给的公里数**（默认 200 公里）在路线上布点；**不改客户给的数字**。
- **优先「不拥堵路段上的服务区」（硬性排序）**：**服务区排不排队，跟路段堵不堵是同一件事**——判断标准是**它所在的那个路段、在那个时段堵不堵**（＝§4/§5 的结论），**不是"服务区一律会排队"**。所以：
  1. **本时段不拥堵路段上的服务区**——**就在主线上、不绕行**，有桩就在这儿充（**首选**）；
  2. 只有**窗口内没有服务区、或服务区没桩、或窗口内服务区全都落在被点名 / 拥堵路段上**时，才下高速进**出口 3 km 内**的城区 / 县城充电站；
  3. **避开充电高峰**：**11:00–13:00、17:00–19:00**——**但若该时段该路段本来就不堵，照常在服务区充**。
- **±50 km 窗口（硬性）**：客户给的"多少公里一充"是**目标值，不是死线**——在 **±50 km** 内挑**不拥堵**的那一个服务区（说 200 km → 在 **150–250 km** 之间选），**写明实际里程**。**窗口内宁可挪 30 km，也不要为了凑整而多下高速绕一圈。**
- **一句话判据**：客户要的「**人不多的充电区**」＝**本时段不拥堵路段上的服务区**——路段不堵，服务区就不排长队，所以**优先在服务区充，不默认下高速**。
- **每个充电点必须给**：服务区名（或「某收费站下高速 → 某地」）、**充电站名 / 运营商**、**到下一个充电点的里程**、**备选 ≥1 个**；桩数与功率**只有查到公开来源才写**（**无公开数据**就不编）。
- **续航折损提示**：高速 / 低温 / 开空调会让实际续航明显缩水 → 提示**留 20% 以上余量**、必要时**提前一档充电**（间隔仍是客户给的数字，**不替客户压缩**）。
- **兜底**：建议随车带便携充电枪，并说明「节假日服务区排队时，下高速充电往往更快」。

### 7.1 电车的中途点 = **充电桩位置**（硬性）

中途点**不要只写城市名**，直接写**要去哪个充电桩**：**首选服务区（写服务区名 + 实际里程）**；服务区不行才写「XX 收费站下高速 → XX 县城快充圈」。**注意：这些充电点不落成 `points.json` 的 `vias[]`**（写进去＝钉住走廊、会改掉地图的最快线）——而是画到总览图上（小蓝点＋水平引线引出服务区名，`shot --nodes`；**图上不编号**）并写进讲解页的途经点表。

**筛桩点的顺序（固定）**：① 按客户给的间隔取 **±50 km 窗口**；② 列出窗口内**所有服务区**，去掉**没桩的**、去掉**正落在被点名拥堵段上的**；③ 剩下取**离目标里程最近的一个**；④ 窗口内一个都不剩 → 才下高速进**出口 3 km 内的城区站**。**每个桩点写清「实际里程 + 为什么是它」。**

**三条评估（不达标就换桩点）**：

| # | 判据 | 不达标怎么办 |
|---|---|---|
| ① **尽量走高速** | **高速占比 ≥ 95%**，且**每个桩点离高速出口 ≤ 3 km**（两条都要满足；不是"非高速段 ≤50 km"那种总量口径） | 桩点从「县城中心」改到「出口 3 km 内的站」或**改回服务区** |
| ② **不能太绕** | 相对**最快线**：里程增幅 **≤ 20%** **或** 耗时增幅 **≤ 30 分钟**（同 §3「太绕」判据，满足其一即可） | 砍掉绕得最远的那个桩点 |
| ③ **不能落在堵点上** | 桩点本身**不落在结论库的高频拥堵段**（§5 排名里的 HIT 段） | 在 **±50 km 窗口内换下一个**；换不了就改错峰，并在页面里写明 |

**桩点必须画到总览图上（硬性，客户点名要求）**：电车的每一次停靠都要在**总览图**上画成**一个小蓝点 ＋ 一条水平引线**（`--nodes` 的点标注：`{"type":"point","color":"#0B72C4","r":7,"label":"巳市服务区","labelDir":"e","lng":…,"lat":…}`（**点必须有 `lng`/`lat`**，缺坐标会被静默丢弃）；总览图 JSON 顶层带 `{"legend":false,"parallel":true}`，**不出菜单**），名字由引线引出；长名／品牌／里程写进讲解页的途经点表。
- **拥堵段＝红点＋水平引线引出段名（）**：原口径「只涂线色、不标点、说明进菜单」已被取代——现在**在主线折线上放一个红点**（大概位置＝该段锚点里程处，`labelDir:"w"`），**用水平引线引出「午县段／辰市段／…」这样的段名**，**图上不写年份次数、不出菜单、不写表**；严重度（点名次数）放讲解页第③段「拥堵解读表」的依据列。
- **总览图不出菜单**（「弄个菜单即可」已升级为「图上只留点＋引线＋名字」；菜单只留给**节点图**）；讲解页里仍要写明**本次读数**的间隔口径：「沿途充电点（非拥堵路段服务区，间隔 X—Y km，本次读数）」＋「每段 ≤ 客户给的公里数（默认 200）＋50 km」——X／Y 按本次实测填，别照抄别次的数字。
- **先检查「服务区是否落在被点名拥堵段里」再定桩点**：实测甲市→丙市的第 1 站原本选了**辰市服务区 267 km**，而它正落在被点名的**辰市段 234.8—288.6 km** 内（绕行时还够不着）→ 必须换成**绕行出口（巳市收费站 234.8 km）之前**的**巳市服务区 231 km**。这一条能被脚本抓出来：把桩点里程逐个塞进 §5 的 HIT 段区间做一次 `∈` 判断。

**取服务区的方法（一次取对，别反复试）**：用地图厂商的**「周边搜索」**（`place/around`，`keywords=服务区`）沿**主线折线**每 **40–50 km**（实测：按 40 km 扫，甲市→丙市主线扫出 **124 个**服务区/停车区；步长必须比客户给的充电间隔**密**，否则会漏掉离目标里程最近的那个）取候选（每个采样点半径 25 km）→ 只留**离主线折线 ≤ 1.2 km** 的（实测口径：服务区/停车区本身就贴着主线，>1.2 km 的基本是对面方向或别条路上的同名服务区——按 1.2 km 扫甲市→丙市主线得到 124 个，没有误捞；**别放宽到 3 km**，那样平行高速上的服务区会混进来）→ POI 名字自带**「高速名 + 方向」**（如「石城服务区(壬高速辛市方向)」），用**行进方位角 vs 该方向城市的方位角**判顺逆向（差 ≤80° 为顺向）→ 按 ±50 km 窗口选**离目标里程最近的服务区**（`服务区` 优先于 `停车区`）→ 再对该点做一次 3 km 周边搜索 `keywords=充电`，**只认距服务区点 ≤500 m 的桩**（实测会捞到对面 / 邻镇同名服务区的桩），**有充电站 POI 才写"可在服务区充"**。**口径**：厂商 POI 的**名称 / 坐标 / 距离**可用于选点，**原始响应不落盘**。

**实测样例（癸市 → 子县 · 电车 · 200 公里，2026-10-01）**：主线 = 最快线 **1623.9 km**（截图 **1624.4 km**）。7 个充电点（实际里程 · 服务区 · 顺向）：
**167 延平服务区 → 401 石城服务区 → 596 吉安西服务区 → 810 耒阳北服务区 → 1015 全州服务区 → 1182 永福服务区 → 1408 雅山服务区**，终点子县 1624（末段 **216 km**，仍在 ±50 窗口内）。7 处**全部离主线 ≤0.2 km、全部查到充电站 POI → 全程不下高速**；桩点所在路段**没有一处落在高频拥堵段上**。

## 8. 输出：**地图截图（贴卡点）＋ 单文件讲解页**

**思路**：不自己画地图——**把途经点交给地图厂商的网页版，由它算路并绘制，再截图**。**截图即交付物**（之一），但**只有图客户一定会问"为什么"**，所以**截图之外必须再交付一份单文件 HTML 讲解页**，把截图**内嵌进去**逐项讲清。**两份一起交，缺一不可。**

| ④ **只留一条线（硬性）** | 再加 **`--single`**（要指定某条先加 `--pick N`） | 高德网页版默认把 **2–3 条备选路线**一起画出来（左侧还列成多张卡片）→ 交付图"很混乱"（实测被客户打回）；`--single` 只对 `--pick N` 指定那张卡执行点击、把**其余卡片与备选折线隐藏**（拥堵着色与底衬不动）；它**不点「偏好」**——要「不走高速」得另加 `--pref 不走高速`（且 `--pref` 必须在 `--single` 之前）。**认线看颜色**（选中＝品牌绿 `#00C86E`、备选＝浅绿 `#9ADEC8`），**不要按"点数多"认线**——短程节点路线的折线点数很少，按点数认会漏清理、图上仍留着备选线 |
| ⑤ **绕行段让地图自己画** | 加 **`--pref 不走高速`**（在 `--single` 之前生效） | 点开页面「偏好」选「不走高速」→ 地图自己算地面路并画线（实测 `午县收费站 → 未县西收费站` 给出 40.3 km／¥3 纯地面）。**URL 参数 `policy=3` 无效**（页面照样给高速），别在链接上白费功夫 |
| ⑥ **出总览图（不钉途经点：用地图默认最快线）** | `points.json` 的 `vias` **留空**；截图后读**图上面板**的里程／耗时作为报告口径 | 「就默认地图最快的高速路线就行了」——**先出图，再按图上这条线**逐段做拥堵分析，图与报告同源。**注意最快线会漂**：同一条链接几十分钟内就可能换走廊（实测甲市→丙市：0 个途经点一次给过 G9111 庚高速 2118.8 km／¥1055，2026-10-17 另一次 0 途经点给 G9112 大广 约 2119 km／22 h／¥1055；钉「酉县」给 2135.9 km／¥1069）→ 一个交付内所有数字取**同一次查路读数**，并在图例／页面写明读数时间与「会浮动」。**只有客户明确要求必须走某条走廊时**才加 **1 个** `vias`（靠终点一侧；实测 1 个与 2 个折线逐点一致，**钉 2 个是多余动作**） |
| ⑦ **电车：把充电点标到总览图上（硬性）** | 在总览图的 `marks.json` 里，按里程顺序追加**小蓝点＋水平引线**：`{"type":"point","color":"#0B72C4","r":7,"label":"巳市服务区","labelDir":"e","lng":…,"lat":…}`（**总览图不加 `legendLabel`、不加 `sep`、不编号**——`legend:false` 下菜单不建、`sep` 不画） | 客户明确要求「**在总路线里把不会拥堵的服务区标出来**，尽可能保证 X ± 50 km 有一个」＋「**充电桩在路线上订一个小点即可，然后拉出一条线引导其服务区名字**」（2026-10-16）。**短名贴点**，长名／品牌／桩距写进讲解页第②段充电清单（总览图 `legend:false`、没有菜单可放长名）；**每个桩点先验过不在被点名拥堵段内**（§7.1） |

**卡点标注规则（硬性）**：
- **拥堵段＝红点＋水平引线（定稿口径）**：`{"type":"point","color":"#C62828","r":5,"label":"午县段","labelDir":"w","lng":…,"lat":…}`，点**必须在主线折线上**（先投影）；**不再用 `type:"line"` 涂线色**（客户要求「只要在总览图里涂上拥堵路线颜色就行了」已改为「用红点标记大概位置」）。
- **严重度由脚本判定，不许人工上色**：`congestion-nodes.js --date <出发日>` 直接输出每个节点的 `level` + `levelWhy`——**深红 high ＝命中 ≥4 次 或 出发年被官方点名；红 mid ＝命中 2–3 次 或 最新命中年份 = 出发年−1；浅红 low ＝其余**（不给 `--date` 时照出 high/mid/low，`mid` 仍按命中 2–3 次判定）。**严重度只做解读表分级、别拿颜色当分级**：总览图拥堵段统一显式给 `color:"#C62828"`（不给 `color` 时脚本会按 `level` 自动配深红／红／浅红，会画回客户已否掉的三色图），`level`／`levelWhy` 只喂第③段解读表与节点图；**`--marks marks.json` 可直接直出 `--nodes` 能吃的标注文件**（省掉手工转，脚本已内置）。
- **所有标注点先投影到路线折线上再画**（或直接取折线端点）：锚点原坐标会飘到线外（实测"丑县收费站"锚点离线 **9.5 km**）。**换走廊后必须重跑 `map-shot.js link`**：`_u_*.txt` 里存的是旧链接时，标注会被投到错地图上（实测表现为标签飞到 1500 px 外、菜单写的段名与底图走廊对不上）。
- **点＝小圆点＋引线＋名字（硬性，定稿口径）**：卡点／充电位／拥堵段在地图上只放**小圆点**（`r` 默认按 level 取 high 11 / mid 9 / low 7，拥堵红点可显式给 5；DOM `AMap.Marker` 画，白边），**用引线把名字引出来**；**总览图用 `parallel:true`**：引线**只走水平**、同侧按 y 排序、`y` 间距 < 24 px 的挤到下一档（横向阶梯外推），**保证不重叠、不压路线**；节点图仍可用自由候选位（26/52/86/126/172/224 px × 四方向）。
- **摆位顺序与验收四数（硬性）**：**有菜单时菜单先摆**（四角＋两个底边共 6 个候选位）→ 标注后摆；**平行模式**先按 `labelDir` 分侧、再按 y 排序排阶梯；所有元素按**压线几何**打分避让；**`shot` 打印 `标注压线 / 标注互压 / 标注退让 / 压线分`——交付前四个数必须全是 0**。
- **避让（硬性，三样都不许压）**：① **不许压左侧「路线面板」**——注入脚本会先**测出面板右边缘**（按位置+尺寸找，别只认某段文字，实测会漏），**标签与菜单都要让开**（实测标签往左推 210 px 会正好藏进面板里、菜单放 `left:16` 也会压在面板上）；② **不许压路线几何**——脚本把**路线（连同我们自己的标注线）投影成像素点集**（**障碍取自 AMap 自己的 overlay 折线采样 ＋ SVG path 采样 ＋ 标注自身几何**，实测 2600+ 点；另把地图控件矩形 `.amap-container *`（有文字、尺寸 24–460×14–130）当障碍，权重更高），**"压线"权重最高**，标注与菜单都在候选位里选分最低的；③ **菜单还要在四个角各试一遍**（`--pref` 出的地面绕行线常斜穿半张图，菜单一大就会盖住），**菜单越小越容易躲开**（限宽 336px、11.5px 字）。标签放不下时先改 `marks.json` 里的 `labelDir`（`w`/`e`）再重出图；`shot` 没有 `dx`/`dy` 参数（写了会报未知参数 exit 1），个别位置用 `--js` 注入微调。
- **图上每条线的来源要写明（硬性）**：图例（仅节点图）与讲解页 note 固定写「**底图与图上实线＝地图自己算路绘制；红／蓝点、引线与名字＝本报告加的标注**」（地面绕行线由地图自己按「不走高速」画、我们不画绿虚线；真要用 `dash:true` 兜底时才在菜单里注明）。**客户会直接问「这条支线是地图的线还是你画的」**——不写清就没法自证。**同一行末尾还要写「底图上金色／彩色小圆点＝高德自带的设施图标（服务区、加油站等），不是本报告的标注」**——底图 POI 图标画在 map 的 canvas 上、DOM 删不掉，还会压在我们画的线上（2026-10-17 客户就问过"总览图里为什么有一个黄点"，见 §9 第 31 条）。
- **菜单（图例）只在节点图用**：总览图 `legend:false`（）；菜单末行仍固定带两句声明（底图/实线＝地图画的、底图金色 POI 图标不是本报告标注）。讲解页 notes 里要出现「严重度」字样（`make_html.js drive --check` 校验）。
- 节点精细图（**仅在需要精细化说明时附 1 张**；已要求删除逐段细则页，默认不出）= 「被绕行的高速段（红点／红段，报告标注）＋ 地面绕行（**地图自己画的绿线**）＋ 出 / 入两点」画在一张图上。
- **耗时分两处口径（硬性）**：地图面板里的分钟数是**查路时读数**，同一天不同时刻也会变（实测 G9112 辰市段 41 min ↔ 37 min）。所以**图例、讲解页 note 都要写明"查路时读数"**，结论**只落阈值**（"该段高速多花超 30 min 才改走"），**不承诺绝对分钟数**。

**② 出讲解页**：`make_html.js drive`（数据只有六块，字段见 `--help`）：

| 数据字段 | 页面章节 | 写什么 |
|---|---|---|
| `coverCards` / `overview.rows` | 封面数据卡 + 决策速览 | 总里程 / 纯驾驶时间 / **充电点数（仅电车；油车换成「不推荐服务区」说明）** / 拥堵段数；每行一条结论 |
| `sections[type=map]` | 第 1 张＝**总览图**（默认唯一一张；细则页已删，需要精细化时才附 1 张节点图） | **每张节点图必须有 `note`**：从哪个口下、走哪条路、从哪个口上、代价多少、堵到什么程度才触发 |
| `sections[type=waypoints]` + `waypoints` | **电车充电清单（只放充电，不掺拥堵；**车辆类型＝油车时整段省略**）** | 每行＝**累计里程 + 充电服务区 + 本段里程 + 桩（品牌·距服务区中心）+ 备注**（第一行是表头）；**拥堵路段的「下口/上口」不进这张表**，统一放第③段拥堵解读表（两类信息分开，不混表）；**`make_html.js drive --check` 会拦**（waypoints 行里出现 收费站／高速口／下高速／上高速／互通立交／匝道 即报错） |
| `sections[type=table]` | **拥堵解读表**（必须有） | 列：**拥堵路段（节点）/ 依据（年·节假日·发布单位）/ 下高速口 / 上高速口 / 预案**（**SKILL.md 收尾段的四列写法是旧口径，以本表五列为准**；`--check` 只强制表头含「依据」「预案」）；**没被点名的也要列**（写"未发现被点名路段"/"未获取"）；`--check` 会校验表头含「依据」「预案」、notes 含「未获取／复核／严重度」；**表里写「需精细化」会触发 `--check` 要图**（每处各 1 张带 `note` 的节点图） |
| `sections[type=grid3]` | 为什么走这条走廊（**可选、默认不出**） | 本线（`mine:true`）对比 1–2 条**不走的线**，写清"正穿哪些被点名路段 + 多跑多少" |
| `sections[type=notes]` | 电桩计划（**油车整项不写**）、时间账与错峰、**未获取项 + 出发当天复核清单**、口径与边界 | 未获取项逐条写明缺什么；复核清单写清**当天按哪条路逐段看实时路况、堵到什么程度触发哪个下道口** |
| `sections[type=sources]` | 数据来源 | 每条结论的年份与发布单位 |

- **讲解页里不许出现技术信息**（脚本名 / 接口名 / 数据源名）——`check_html.js` 的 **A7** 会拦；**官方发布单位名、年份、节假日照写**。
- **顺序固定**：先出截图 → 再生成讲解页 → 两件一起交。
- **口径**：**里程与耗时以图上为准**（地图会带入打开时段的路况，耗时有 ±40 分钟浮动；**里程与「首推哪条走廊」都会随实时路况变**——所以一个交付内的图、页、报告必须取**同一次查路读数**并写明读数时间；只有客户指定走廊时才按 §8 ⑥ 钉 1 个途经点）；同口径接口复算作参考。

**`points.json` 是我们的方案骨架**：`from`/`to`（`name` + `lng`/`lat`）、`vias[]`（避堵=**地面走廊途经点（加密）**、钉两端=**下道口 + 上道口**、客户指定走廊时才钉主线关键点；**总览图默认留空**——电车充电点也不写进来，改画蓝点标注）、`coord`（`gcj02` 默认 / `wgs84` 自动转）、`policy`（0 推荐 / 1 避拥堵 / 2 避收费 / 3 不走高速——**⚠ 网页版链接上的 `policy` 实测无效，要"不走高速"只能点页面「偏好」或出图用 `--pref`**）。
