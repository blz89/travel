# 流程二：目的地景点分析 → HTML

> 本文件由 `SKILL.md` 指向。**进入流程二时必读**。
> 关键口径（景点数量与配比、网址形状闸门、开放时间必查）在 `SKILL.md` 正文有摘要，本文件是完整步骤。

### 流程二：目的地景点分析 → HTML

- **生成时机（硬性，提速）**：公共交通「由我提供方案」分支——**景点预研产出就绪后就开始生成景点页**（步骤 5～6：生成网页 → 校验），**最迟在流程一「弹出出行方案选择框」之前完成**：用"等交通数据 / 整理方案"的空档把这件事做掉，**不要等客户选定才动手**。**依据**：景点页的内容**完全不依赖客户选哪条路线**（只有行程方案页依赖到达站），提前做永远不会白做；客户选定后只需**打开**，那段等待就省掉了。**预研尚未就绪时不要停下来等**——照常弹「出行方案选择框」，景点页改在客户选定后按步骤 5～6 顺次生成（兜底路径）。
- **打开时机（硬性）**：**同一时刻只打开一个网页，且景点页必须排在客户选定之后**。流程一打开的是**交通方案页**（同时弹「出行方案选择框」）；**客户选定之后**才**打开**景点页，并接着走步骤 7 起（景点多选框 → **是否需要景点路线规划［是 / 否］** →〔**选「是」才继续**〕→ 出发点选择框 → 行程方案）。**客户选定之前绝不打开景点页**——**绝不允许交通页与景点页同时弹出**（客户会分不清该先看哪一份，也会先看到景点而没定路线）。没有城际选择框的分支（已有出行方案 / 自驾 / 已在目的地）不受此限，直接进本流程、从步骤 5 顺次做完并打开。
- **进入本流程第一件事 = 取「景点预研分工」的产出**（见下条「输入」）；**景区间移动类别**由第一阶段的选择决定：
  - 自驾 / 已在目的地·自驾到达 → 景区间按**自驾**；
  - 公共交通（城际）已选方案 / 已在目的地·非自驾到达 → 景区间按**公共交通**（含打车/公交/步行）。
- **输入**：**景点预研产出**（`<目的地>景点数据.json`，取用方式与兜底见「景点预研分工」）；目的地；景区间移动类别（自驾 or 公共交通）；若公共交通城际已选定方案，还含到达站/到达时刻（用于排景点顺序）；行程日期（若可确定）。
- **处理步骤**（顺序执行，全部产出后再交付）：
  1. **搜集目的地旅游景点信息**：用 `web_search` 到**旅游景点介绍网站**获取信息（推荐：景区官方旅游网站、当地文旅局公示、马蜂窝 mafengwo、去哪儿 qunar）。**优先选目的地本身的景点**；若目的地凑不齐 5 个，按**就近原则**扩大到同城/周边（邻近城市、度假区、县域，标注"距目的地约 X"）。
  2. **筛选景点数量与类型**：最终入选 **5～10 个**景点，其中**至少 2 个热门景点**，并且**保底推荐 2 个不热门景点**（**这三条由生成器硬校验**：数量或配比不达标会被直接拒绝生成，所以 meta 里要写清"热门 / 不热门"）。给每个景点标注：类型（自然/人文/历史/主题乐园/博物馆等）、预估游览时长、**开放参考时间与闭馆日**（如"08:30-17:30 · 周一闭馆"，**查不到就写"以景区公示为准"——不许留空**）、距离目的地/到达站的远近与到达方式。
   - **预研阶段的提前门禁（硬性）**：上面这些规则（数量 / 配比 / 网址形状与评审 / 字段 / **开放时间** / 来源 / 封面卡统计一致）已固化成**一条命令**，**预研子代理产出后必须自己先跑**：
     ```
     node scripts/spots_check.js <目的地>景点数据.json
     ```
     **必须 exit 0 才能交回**；FAIL 就按它列出的条目自己改数据、重跑（**最多 2 轮**，过不了就连同输出一起交回）。
     **为什么**：这些规则原本只有生成 HTML 时才检查，那时子代理已结束、主流程要**跨进程返工**（重派子代理或自己补做）；提前到子代理内部自查，返工就消在它自己的上下文里。
     - **开放时间/闭馆日（必查项）**：用 `web_search` 查每个景点的开放时间与**闭馆日**（**必按该馆官网最近 1～3 个月的公告核对**——节假日/旺季常临时调整：取消周一闭馆、延时、临时闭馆；**不得默认"博物馆周一闭馆"**，山岳类另注意索道/观光车末班时间）。此信息用于：① 景点页的景点信息行；② 「行程方案规则 → 开放时间提示」要求的那些提示。
  3. **为每个景点给一条「景区介绍网址」（只给一条，必须过评审）**：选源顺序见 `references/spots-research.md`「选源顺序（硬性·五档）」；`spot_link.js` 给出的 `source` 要写进 `urlLabel`（如「景区介绍（官网）」）。
     - **优先当地文旅局 / 景区管委会 / 景区官网的「概况 · 简介 · 景区介绍」页**：要点式（面积、等级、历史、主要景点），最好带图。实测这类页面比官网首页信息密度高、比攻略站权威。**只给一个网址，不要给多个**（客户不会逐个点）。
     - **可达性先过一遍（省 5–8 次 `web_fetch`）**：
       ```
       node scripts/spots_urlcheck.js check <url> …   # blocked / dead / thin 直接丢，只把 ok 的交给下一步
       ```
     - **评审机制（硬性，不许自评）**：
       ```
       node scripts/spot_link.js resolve --name "<景区名>" --url <候选1> --url <候选2> --cache
       ```
       输出 `SPOT_LINK … grade=A|B|F`：**A**（要点 ≥10 且图 ≥3）/ **B**（要点 ≥5）→ 把 `intro` 填进 `url`，`urlLabel` 写"景区介绍"；**F**（没有合格介绍页）→ **`url` 留空**、`urlFallback` 写"以景区公示为准"、`urlLabel` 写"暂无官方介绍页"。
       `spots_check.js` 的 **B8** 会核对 url 与评审缓存一致、评审 ≤90 天；F 级必须留空 + 写降级文案。**"我觉得这个网址不错"过不了 B8。**
     - **门票三态（只回答"要不要买票"，不写价格）**：`ticket` 写 `paid` / `free` / `free_with_fee_parts`（后者用 `parts` 列园中园、索道、摆渡船等另收费的子景点）。
     - **形状闸门（`scripts/lib/validate.js`，生成器与 spots_check 同源）**：拒绝短链 / 纯 IP / 反爬特征 / 携程系（trip.com、ctrip.com）/ 政府信息公开与政务目录页（xxgk、zwgk…）/ 频道栏目首页 / 政务稿页（仅 `*.gov.cn` 的 `/t日期_编号.html`）。**文旅局、管委会、省政府的「概况/介绍」文章页是合格的**——别因为"是政府站"就放弃这类最好的页面。
     - **不要逐个 fetch 验证、不要整页读取**：交给 `spot_link.js`（内部只读前 160KB，不进上下文）；已知反爬站（百度百科 403、携程验证页、部分管委会 WAF 412）直接跳过换下一候选。
  4. **为每个景点撰写文字内容（好评/差评各最多 2 条；我的点评可更细致）**：
     - **条数：最多 2 条，允许更少**：优先写满 2 条；**公开评论确实很少时，允许只写 1 条甚至一条都没有**——空的那一栏**整栏不渲染**（因为没东西可写，不是遗漏）。**不得编造**，也**不得**把同一条拆成两句充数；缺少的那一栏在该景点 `source` 里按本步骤的「评语来源标注」如实写明"公开评论较少"。
     - **景区好评（最多 2 句）**：一～两条**有代表性**的好评（参考该景点评论/点赞量，选真实游客普遍赞扬的点，如风景、服务、性价比、交通便利等；多条分开写；素材不够就少写，不要凑）。
     - **景区差评（最多 2 句）**：一～两条**有代表性**的差评（参考评论/吐槽热度，选真实高频或典型的点，如人多、排队、商业化、交通不便、性价比存疑等；多条分开写；素材不够就少写，不要凑）。
     - **我的点评（这一栏是整页唯一"有人味"的地方）**：**合计 ≥24 字**（生成器会拦 <24 字），1～3 句；判断要明确、**落在具体动作上**（几点到、从哪个门进、哪段坐车、哪段腿着走、值不值那趟绕路），**语气像人说话**：可以幽默、可以有画面感、可以小小吐槽，别端着写导游词。
       - 好：「八点前进园，前两小时基本是包场；十点以后中轴线上全是小旗子，拍张照要等三轮。腿脚不好的长辈建议从午门进、直接坐摆渡到神武门往回走，省一半路。」
       - 好：「值，但别信"半小时逛完"的攻略——光是排队买那碗牛肉面就半小时，吃完你会觉得这趟绕路是值的。」
       - 差（别这么写）：「景色优美，历史悠久，值得一游，建议提前规划。」→ 全是形容词、没有一句是"你的"判断，读起来像抄简介。
       - 硬底线不变：**不得编事实**（票价、班次、开放时间只能来自 meta / 官方公告），幽默不等于瞎编；好评差评照旧最多 2 条。
     - **评语来源标注（硬性要求）**：好评/差评不得凭空发挥，必须标注**归纳依据**——写明来源平台与评价类型，如"来源：马蜂窝 / 去哪儿 / 大众点评 游客高频评价归纳"。（**注意**：「评语来源」与步骤 3 的「景点网址」是**两回事**——网址有形状闸门，携程系与政务站**不能当网址**；但评语来源只要求**如实标注你实际看过哪个平台的评价**。）在**聊天回复**中逐景点标注来源；**景点页也须加一行来源标注**（小字灰色，不占正文位置）。若该景点公开评论极少，如实写"公开评论较少，以上为综合攻略信息归纳"。
     - **诚实边界**：评语代表**游客普遍反馈**，不得虚构具体数字（如"99% 好评"）或引用不存在的原话；不确定的表述用"多数游客反映""部分游客提到"。
     - **先在骨架上改，不要从空 JSON 手写**：`node scripts/spots_emit.js <selected.json> --out 景点数据.json --note "本次假设"` 一次把封面卡统计 / 总览表 / 网址三轨（自动读 `spots-links.json`）/ 门票三态填好，你只补 good / bad / mine / source 四类文案。
   4.5 **闭馆 / 闭园核查（硬性，机器判、不靠心算）**：景点入选后先跑一遍——

       `node scripts/hours_check.js <景点数据.json> --arrive <到达时刻> [--days <停留天数>] [--buffer 60]`

       - `--arrive` 取法：**公共交通** = 客户所选方案的**到达站/落地机场到达时刻**；**自驾城际** = 计划出发的时刻（配 `--buffer 180`，把当天车程算掉）；**已在目的地** = 客户给的当天日期（可只写日期，按全天可游判）。`--days` = 停留天数（含到达当天）。
       - 三种结论照做，**不许自己心算**：`closed`（游玩期内全闭）→ **当场剔除**，补 1 个备选景点、补足 5～10 与热门/不热门配比；`shift`（当天闭馆或来不及）→ 按脚本给的「可游日」把它排到那一天；`tight`（入场余量 < 60 分钟）→ 照排，但在该景点行注明「当天直奔，来不及改次日」。
       - `unknown`（景区只写「以景区公示为准」）→ 按可排处理，页面 meta 保留该兜底写法。
       - 只认 data.json 的 `spots[].meta`：写清「周一闭馆 / 法定节假日除外 / 11月-次年3月闭园 / 16:00 停止入馆」这类事实，脚本才判得出来；meta 里没写的闭馆日一律视为未知。

  5. **生成网页（总、分形式；用参数化生成器）**——**步骤 5～6 属于「生成时机」，应在客户选定出行方案之前就做完**（见本流程开头）：
     - 生成与出稿的命令**见下一步**（一条命令：生成 + 校验）；这里只说数据要写什么。
     - 数据结构：`coverTitle/coverSubtitle/coverCards/coverNote` + `overview`（总览表：rows + colWidths（数字权重）+ note；注脚三种写法 `footnotes` / `note` / `noteBox` 通用）+ `spots[]`（每景点：`name`、`meta`（类型·时长·**开放时间/闭馆日**·距离·热门标签）、`urlLabel`+`url`（景区介绍页，超链接；F 级则 `url` 留空 + `urlFallback`）、`ticket`（可选，门票三态）、`good[0~2]`、`bad[0~2]`、`mine[1~2]`、`source`（评价来源））。
     - **总览块**：先把全部推荐景点**集中列出来**（景点名 + 类型 · 时长 · 距目的地 + 热门/不热门标签），让用户对整体一览无余（**"总"**）。
     - **景点多不会挤**：网页是连续滚动的，景点越多只是页面更长，不存在「一页放不下」——**不要为了排版去砍景点数或砍文案**；总览表与卡片一律由生成器统一排布。
     - **每景点一张卡片**：由生成器渲染——你把 `name`/`meta`/`urlLabel`+`url`/`good`/`bad`/`mine`/`source` 填全即可；**箭头、按钮提示语、三栏并排、空栏不渲染、来源小字一律由生成器处理，数据里不要写**。
  6. **生成 + 校验（一条命令）**：`node scripts/make_html.js spots <景点数据.json> <景点推荐.html> --check`
      —— `--check` **自动带 `--spots`**（景点页允许"评价来源行"；不加会把"马蜂窝/去哪儿"误报成技术信息，见 A7）。
      （**生成属于"提前做完"的部分，不必等客户选定**；对客户只体现「打开」这一步）——景点页含可点击的景区介绍网址，HTML 里照样能点。
      **校验 FAIL 时脚本拒产并删掉未过校验的 HTML**；改数据后重跑同一条命令，**不要再单独跑 `check_html.js`**。
  7. **弹出「景点多选框」**：`ask_user_question`（multi_select）列出**全部推荐景点**，**必须带"全选"**（可一键打钩全部）选项。用户勾选要纳入本次行程的景点（可全选，可只选部分）。**若客户取消了部分景点**，已生成的景点页仍列着全部推荐景点——此时**不要重新生成景点页**（它本来就是"推荐页"，列出全部是对的），只按**客户实际勾选的**做后续行程方案，并在聊天里说清"行程按你勾选的 N 个景点排"。
  8. **弹出「是否需要景点路线规划」选择框**：`ask_user_question` 单选，**选项只有两个：是 / 否**。问题文本里**必须原样带上这句说明**（标点可微调，信息量不得删减）：
      > 「选『是』就接着为你排景点之间的路线与顺序；**也可以在下方输入框补充推荐名单之外、你自己想去的景点**，会一并纳入路线规划。」
      - **选「是」** → 继续走步骤 9（出发点选择框）起；**路线信息此刻才开始取**——先把起始点定下来（步骤 9）、再在步骤 10 取数与排线，**不做任何预取、不在客户选景点之前预先收集路线信息**。
      - **选「否」** → **跳过步骤 9～11**：不弹出发点选择框、不排行程、不出行程方案页，**也不发起任何路线相关查询**；**景点推荐页照常交付**，直接按「收尾：一句话交还」收尾。
      - **客户在输入框里补充了景点**（没按选项选、直接打字；**选了「否」又补充景点 → 同样按「是」处理**）→ 视为**「是」+ 追加景点**：**不回退、不重新生成景点推荐页**（推荐页保持原样、仍只列推荐景点），**只把这些景点并入本次路线规划**；补充景点的**开放时间/闭馆日同样要查**（查不到就写"以景区公示为准"），并在**行程页与聊天回复里标明这几处是客户自行补充的**。**不要**因补充景点去改景点推荐的数量与热门/不热门配比——那套校验**只约束推荐页**。
      - **本框只问一件事**（要不要路线规划）：补充景点是它的**可选附注**，**不算第二个问题**，与「一次只问一项」不冲突；客户没补充就按勾选的景点排。
  9. **弹出「出发点选择」选择框**：`ask_user_question` 单选（**只有两个选项**），让用户决定**从哪个景点开始**：
      - 选项① **「从到达地出发，选最近的景点作为起始点」**（推荐、默认）——取距参照物**最近**的那个景点作起点，**参照物按分支定，见「通用要求」**；
      - 选项② **「我来自己决定第一个景点（下方输入）」**——问题文本里**列出全部推荐景点**（供用户对照），用户直接在**下方输入**想第一个去的景点，即以其为起点。
      - **参照口径与串线方式统一见「行程方案规则 → 通用要求」**，此处与自驾/公共交通两小节都不重复。
  10. **生成旅游出行方案**：按「行程方案规则」执行（含**景区间移动类别**的两种口径、**不按天数拆分**、**逐站站点级**、**首段出发地口径**），在聊天回复中输出。
  11. **制作行程方案网页（用参数化生成器）**：
      - 命令：`node scripts/make_html.js itin <data.json> <out.html> --check`（生成 → 校验；FAIL 会拒产并删掉未过校验的 HTML）
      - 数据结构：`coverTitle/coverSubtitle/coverCards/coverNote`（封面，含串线） + `overview`（总览表：rows/colWidths（数字权重）/**`footnotes`**，三种写法 `footnotes` / `note` / `noteBox` 通用） + `legs[]`（每段：`n`/`from`/`to`/`km`（**必填**）/`bus`/`taxi`/`note`（可选）/`car`） + `legsFootnote` + `plans`（方案对比卡：**公共交通必给**；自驾给最快/条件满足时的错峰卡。可给卡片数组 `[{title,price,note,tag,rows,badge,hot,hotLabel}]`，也可给 `{title,subtitle,cards[...]}`；缺 `title` 时用「移动方案对比」） + **口径文案（可选，自驾用）**：`legsTitle`/`legsSubtitle`/`legLabel`/`taxiLabel`/`carLabel`。
      - **只写内容**（走法、耗时、费用），**不要带渲染前缀**——**但带了也没事，生成器会自动剥掉**（`legNo` / `stripLead`），不必为此反复检查。
        - `km` 与 `note` 在页面上合成一行「里程 · 说明」，留空的部分自动不显示。
      - **页面结构**（公共交通 / 自驾**共用同一套渲染，不新增页面类型**）：封面 → 行程总览 → 逐段明细（宽屏两列）→ 方案对比卡。
        - **公共交通口径（默认）**：逐段写 A → B 的走法、距离 / 耗时 / 费用，并给全程打车备选；对比卡 =「公共交通三方案」（各含估价）。
        - **自驾口径**：**只给自驾路线，不查也不写公共交通**；对比卡 = 最快路线 ＋（可选）**避峰方案**（由 `scripts/spots_peak.js` 算，见 `references/phase-2-itinerary.md`「两套方案」）。**切换靠数据字段**（`legsTitle` / `legLabel` / `taxiLabel` / `carLabel` / `legsSubtitle`），**无需改代码**。
        - **生成器已替你兜底的事（不必反复自查）**：`n` 写不写「第 N 段」都行（`legNo()` 会剥前缀）；`bus`/`taxi`/`car` 带不带「公交+打车 / 打车约 / 全程打车备选」前缀都行（`stripLead()` 双重剥离）；字段留空则该行不输出，`km` 与 `note` 合成一行、任一侧为空都不会留下悬空的「 · 」。
      - **方案卡的逐段明细不必手写**（省输出，也防止"明细改了总价没改"）：卡片给 `mode` 就由生成器**从 `legs[]` 自动生成明细行**——
        `mode:"taxi"`（全程打车，取每段 `taxi`）、`mode:"bus"`（公交+步行，取每段 `bus`）、`mode:"mixed"` + `taxiLegs:[1,3]`（指定第几段打车，其余走公交）；
